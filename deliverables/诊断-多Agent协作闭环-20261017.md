## 〇、一句话病根

> **这个系统是「文档驱动」的，不是「契约驱动」的。**

契约的代码真源只有一处（`risk_rules.py`），但描述它的文档有 **12 处**，且没有机器强制它们与代码一致。
Agent 启动时读哪份文档**没有强制顺序**，读到哪份算哪份 —— 读到 `RULES.md` 的就按 8% 干活，读到 `AGENTS.md` 的就按 10% 干活。
系统改完之后**没有广播机制**，谁改的谁知道。

于是「旧文档带着旧口径继续发号施令」不是意外，是**结构性的必然**。

## 四、闭环应该长什么样（草案，待你拍板）

```
契约单一真源（risk_rules.py + 交易规则追溯矩阵）
        ↓ 机器校验（每次提交/每日）
   所有文档 / 记忆 / agent 配置 / 技能 与真源比对，不一致即红
        ↓ 变更触发
   自动广播到全部 agent 的记忆入口 + 看板 + 飞书
        ↓ 会话启动
   强制加载「带校验戳」的 bootstrap 清单（顺序固定）
        ↓ 执行
   回测/因子链路代码连通，不是靠人串
```

**四条硬机制**（缺一不可）：
1. **契约机器校验** —— 文档里出现与真源不符的契约数字，测试直接红（我已用 AST 守卫做过止损/阶梯，可复用扩展到文档层）
2. **变更广播协议** —— 谁改了契约，必须向全 agent 广播 + 写 CHANGELOG + 更新长期记忆，否则合入无效
3. **单一 bootstrap 清单** —— 一个文件、固定顺序、带校验戳；其余文档降级为指针
4. **记忆有效期** —— 长期记忆条目带 `verified_at`，超过 N 天自动标「待复核」
