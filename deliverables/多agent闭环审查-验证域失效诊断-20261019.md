### 🟡 断裂 3：消息投递器把 P0 与 P2 平等抑制（已实测正在发生）

**证据**（`data/drain.log` 06:09 / 06:14 两轮实跑）：
```
[suppress] key=plain|🔔 时间止损日期解析失败 [entry_date_invalid]  age=55min window=60min
[suppress] key=plain|🚨 [代码同步环P0] 推前 pytest 门禁不绿 — 不推(F4  age=45min window=60min
[suppressed] count=3 window=60min
[OK] sent=0 fail=0
```

**代码依据**（`cron_message_sender.py:327-333`）：
```python
def _suppress_key(text):
    """抑制 key = 首告警段 '[Pn] <checker标签>' + 前 80 字"""
    t = text.strip()
    m = _re.match(r"(\[P\d\])\s*([A-Za-z][\w]*_[\w]+)", t)
    if m:
        return m.group(1) + "|" + m.group(2) + "|" + t[:80]...
    return "plain|" + t[:120]...
```

**缺陷**：`_suppress_key()` **只吃 `text`，完全不看 `priority` 字段**。
消息体里的 `priority: "P0"` 在判抑制时被丢弃，P0 与 P2 共享同一个 60 分钟窗口。

**当前实证后果**：`data/message_queue.json` 里躺着的
`gitsync_p0_20261019054118`（P0，pytest 门禁不绿导致代码同步停摆）已 **45 分钟未投递**，
且按 60 分钟窗口推算，**窗口过后仍不会自动发**——
`_suppress_key` 对 `plain|` 前缀的文本只按内容去重，窗口到期后会再发一次，但这条 P0 已经损耗了 45 分钟。

> **架构定性**：这是「去重」与「限流」两个关注点被塞进同一个键。
> 去重键应该只管**同一事件的重复**，限流应该按**优先级分层**。
> 现在两者耦合，导致 **P0 被 P2 的噪音拖慢**——这在一个资金安全系统里是不可接受的优先级倒置。

## 五、架构诊断：三个限界上下文被压平了

| 限界上下文 | 应当承担 | 实际承担 |
|---|---|---|
| **执行域**（做了什么） | 产生动作与产物 | ✅ 完整 |
| **验证域**（做了是否有效） | 断言、验收、销账 | ❌ **退化为「存在性检查」** |
| **治理域**（有效性谁裁决） | 交叉校验、冲突仲裁 | ❌ **不存在** |

**核心反模式：验证域与执行域共用同一套「文件在不在」的判据。**
只要验证域的判据是"文件存在 + 台账有登记"，它就永远无法发现
"执行域已经停摆"这件事——因为停摆不会删除文件，也不会删台账行。

> **引用架构师原则**：这不是「实现 bug」，是**判据选错了维度**。
> 任何"存在性断言"在架构上都不构成"有效性保证"，
> 无论它写得多认真、跑得多勤。

## 六、两个方案（附推荐）

### 方案 A：断言从「存在性」升级为「有效性」（推荐）

**做法**：给 5 条弱断言各加一条**读侧实证**，即断言「产物的新鲜度 + 数量」，而非「文件的存在」。

| 断言 | 现状 | 升级后判据 |
|---|---|---|
| A3 | `feedback_log.jsonl` 非空 | **近 48h 有新增行数 > 0**（存量不算） |
| A5 | 检测器文件存在 | **近 7 天 `weekly_ic` 产出 mtime 在窗口内** |
| A6 | 台账里有 `self_audit` | **`laosi_audit/` 最新文件 mtime < 36h**（对齐它的真实周期 24h + 冗余） |
| A1 | size > 100B | **A1 断言自身也要有"上次运行时间"字段**，超期即 PARTIAL |
| A8 | commit 数 ≥ 3 | **每个 commit 声明的 evidence 文件真实存在** |

**同时加一条元断言 A0「体检器自检」**：
> `closedloop_health.py` 把自己的 `last_run` 写进 history；
> 任何消费者读到 `last_run` 超过 2× 周期，必须直接判 FAIL 而不是沿用上次分数。

**权衡**：
- ✅ 改动小（只改 `closedloop_health.py` 一个文件，约 60 行）
- ✅ 直接杀死断裂 1、断裂 2 的"假满分"路径
- ⚠️ **代价**：会立刻把当前状态从 10/10 打到 PARTIAL —— 这是**好事**，
  但必须先向老大知情（铁律：会让门禁由绿转红的事必须先请示）。

### 方案 B：引入独立治理域（更彻底，但成本高）

**做法**：新建 `scripts/governance_arbiter.py` 作为唯一仲裁者，
交叉校验三个体检器的输出并检出矛盾：
```
断言规则：若 closedloop_health 报 PASS 而 defect_ledger 存在 open P0 → 判 FAIL
```
**权衡**：
- ✅ 从架构上真正分开验证域与治理域，矛盾检测自动化
- ❌ **代价大**：新增第四个组件，需要给它自己的监控（否则它也停摆没人知道）
- ❌ 违反本项目既有铁律「不做架构宇航员」——为了治一个「停摆 36h」引入一个新常驻组件，
  换来的复杂度超过收益
- ❌ 治标不治本：新仲裁器照样可能只验「文件存在」

### 📌 我的推荐

**选方案 A，且分两步走：**

1. **第一步（本周，只改一个文件）**：A0 元断言 + A3/A5/A6 有效性升级。
   预期结果：体检器当场由 10/10 转 PARTIAL，**这是暴露真问题，不是引入新问题**。
2. **第二步（第二步单独拍板）**：断裂 3 的优先级倒置修复
   （`_suppress_key` 增加 priority 分层，P0 不参与 P2 抑制窗口）。

**选 A 不选 B 的理由**：
方案 B 的核心价值是"自动检出矛盾"，但**方案 A 做完之后，矛盾本身就不会再产生**
（体检器停了会自己判 FAIL，根本不需要第二个仲裁器去发现它）。
**在根因处修，比在症状处加检测器更符合"复杂度守恒"。**

### ① A11 跨体检器交叉校验（治理域下沉）

**规则**：缺陷台账存在 open P0，而本报告**没有任何 FAIL 项** ⇒ 治理失效，判 **FAIL**。

这条直接杀死「43 条缺陷 0 销账 + 健康度满分」这个矛盾。设计要点：
- 若本报告**已有** FAIL（当前正是 A5），说明问题已被捕获 ⇒ 降为 **PARTIAL**，不重复计矛盾
- 只有当「台账一堆 P0，报告却全绿」时才 FAIL —— 这正是最危险的假绿形态
- 实现上 A11 是**后处理断言**：先跑完其余断言，再把「是否有 FAIL」喂给它

**实测**：

### ② A12 调度载体诊断（与 A0 组合定位故障层级）

| 组合 | A0（跑了吗） | A12（有载体吗） | 诊断 |

| 停摆-无载体 | 旧 | **FAIL** | 建了也不会跑 → 缺载体 |
| 停摆-有载体 | 旧 | PASS | 有载体但没跑 → 调度器故障/被禁用 |

这一点已写进 A12 的 docstring，避免后世误解为自我矛盾。
