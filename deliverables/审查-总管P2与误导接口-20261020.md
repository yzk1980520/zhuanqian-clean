## 二、审查结论：**P2 按原计划不可执行**

不是"分层方案好不好"的问题，是**三个问题的前提都不成立**。

### 2.1 问题②的前提是错的——「未跟踪」在这个仓里恰恰是**最高危**

总管清单写「102 tracked / 33 未跟踪低危」。实测（10-20 01:2x）：

| 项 | 总管清单 | 实测 |
|---|---|---|
| `scripts/` tracked | 102 | **159** |
| `scripts/` 未跟踪 | 33（称低危） | **17** |

根因：10-19 老六的 commit `be3ddf9a` 把 17 个 A 级加进 gitignore 白名单，总管手里是 10-19 之前的快照。

**而这 17 个"未跟踪"的真实身份**（我 10-19 commit message 原话）：
`Zhuanqian_FactorIC132d/Rotation132d/WalkForward` 的 `.bat`+`.task.xml`、
`factor_ic_132d_refresh.py`、`pre_pick_gate.py`、`s3_auto_pipeline.py`、
`walk_forward_*.py`、`audit_delisted_coverage.py`、`check_backtest_result_fresh.py` …

**实盘/调度/门禁直连的命脉。**「未跟踪」≠「低危」，在这里恰好相反——因为它们连 commit 锚点都没有，**换机即丢**。

### 2.2 问题①的两个目的地都会让文件**静默掉出版本库**

老六 `/tmp` 三路复现实验（复刻本仓 `.gitignore:15 scripts/*` + 83 条 `!scripts/xxx` 结构）：

| 执行方式 | git status | 文件还在 git 里？ |
|---|---|---|
| `git mv` | **R** rename | ✅ 在 |
| 普通 `mv` + `git add -A` | **只剩 D** | ❌ **静默掉库** |
| 普通 `mv` + `git add -A -f` | **R** rename | ✅ 在 |

`git check-ignore` 实测：移到 `mainline/factors/` → 不被忽略（安全）；
移到 `archive/scripts/` 或 `.agent/regression/` → **被忽略**（`.gitignore:162` / `:95`）。

**最要命的是第二种情况的三个特征同时成立**：文件**仍在盘上**、`git add -A` **不报错**、
status 看上去就是一次正常删除。102 个文件的人工 move 只要混用一次普通 `mv`，就静默丢一个
tracked 文件，**要等到换机 clone 时才被发现**。

（我早先一度判断"不会掉库"，那是因为我用的是 `git mv`。两个实验都对，差在**执行方式**——
这正是最容易被 102 次人工操作磨掉的东西。）

### 2.3 问题③的两个选项都覆盖不到真实执行面

实测（PowerShell 工具遍历 30 个任务 XML）：

- `cron_config.json` 只登记 **6/30** 个计划任务
- **17 个任务的 XML 硬编码仓库内路径**（23 个路径点）
- `scripts/run_path_hidden.vbs` 是 **11 个任务共享的单点**（我 PS 工具实测；qa 成员报 12，差 1，以 11 为准）

⇒ 选 A（check_all 映射表）生成不出计划任务面；选 B（人工过 cron_config）**只覆盖 6/30，漏 23 个**。

**更深一层**：`cron_config.json` 本身就是一套**假调度系统**（详见 §四）。

### 2.4 引用面比预估大一个量级

- **193 个** `scripts/*.py` 在做 `sys.path.insert`（不是先前以为的 28）
- 全仓引用点 **850+**：md 695 + `check_all.py:174` assert 52 + 计划任务 17 + shell 47 + py 30 + cron 8
- **159 个 tracked 文件里 134 个被引用，真孤儿只有 22 个**
- 两道守卫会因移动而红：`tests/test_no_phantom_script_refs.py:29-40`（锁 9 份治理文档约 31 处引用）、
  `check_all.py:174`（assert 52 条映射）
