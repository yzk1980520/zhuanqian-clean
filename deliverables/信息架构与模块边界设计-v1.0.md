## 1. 信息架构（目标目录结构）

### 1.1 设计原则（四条，对应全局铁律）

1. **按"是否有副作用"分层**，不按"业务名词"分层。纯计算下沉 `engine/`（可单测、可重放），带 IO/告警的上浮 `pipeline/` 与 `ops/`。这是本项目最大的结构病因（见 §2.4 循环依赖）。
2. **一个能力只有一个载体**，同名的其余全部删除，不留兼容层、不留转发壳。
3. **研究态与生产态物理隔离**：`research/` 下的代码**禁止**被 `app/`、`pipeline/`、`engine/` import。用目录边界强制，不靠自觉。
4. **数据区单一**：所有运行时状态只在 `data/`，代码目录内不落任何 `.json` 状态文件（当前 `tdx_score/data/industry_heat.json` 就违规【实测】）。

### 1.3 根目录 .py 数量核算

| 方案 | 根目录 .py | 做法 | 我的判断 |
|---|---|---|---|
| **A（推荐）** | **1**（`main.py`） | 全量下沉；`scripts/` 的 445 个历史脚本整体移入 `research/_legacy/` 只读 | 满足"结构随便拆"，零兼容层。风险：445 个脚本 import 全断 |
| B（稳妥） | **≤25** | 权威载体（`tdx_core`/`risk_rules`/`atomic_json` 等）留根目录，其余下沉 | 风险低，但保留扁平 import 假设，"冗余为耻"打折 |

**推荐 A**。理由：`scripts/` 的 445 个脚本里，被计划任务直接调用的只有 ~15 个【实测：22 个计划任务，去重后入口 ~14 个】；其余是一次性分析脚本，归档后不再维护 import 是**正确**处置，不是损失。继续为它们维持扁平根目录，等于为 445 个死文件约束整个系统的结构。

> 此条属**结构层**，老大已授权可推翻；但需架构师拍板风险敞口 → 见 §8 O-1。

## 9. 我认为最该"推倒重来而非改造"的一处

### ★ `tdx_score` 整族（`tdx_score_original.py` 2268行 + `tdx_score/` 包 13py + `tdx_score.py` 61行壳 + `_score_engine.py` 转发壳）

**理由（四条，全部实测支撑）**：

1. **它是"兼容层套兼容层"的四层洋葱**，本项目踩坑史的活标本：
   `tdx_core` → `tdx_score/`包 → 一半自己实现、一半 `tdx_score_original.py` → 而 `tdx_score.py` 又把这个包再 re-export 一遍 → `_score_engine.py` 再转发一次。
   **四层里真实干活的是最底下那一层。** 每层都是"为了不动调用方"而加的，每层都在增加"改了没生效"的概率。

2. **它已经产生过真实的静默降级**：同样的手法在 `integrated_picker` 上已经爆了（X-3）—— 包遮蔽了权威文件，系统被迫用 `spec_from_file_location` 手工硬加载绕过。`tdx_score` 是**同一套手法、同一个作者、同一个时间点（2026-09-23 Phase C-2）**的产物，只是还没爆。

3. **改造的成本高于重写**：要"改造"就得逐函数比对 6 对同名实现（`heat`/`ranker`/`contribution`/`market_state`/`trailing`/`utils` 各两份）确认行为等价，再逐个切调用方——而这个比对本身**没有 golden 测试兜底**。重写则是：以 `tdx_score_original.py` 为准切出一个干净的 `engine/score/`，用一次全市场回归对比新旧分数分布即可验收。

4. **它是循环依赖环的核心节点**（§2.4），只"改造"不动分层，环还在。

**推倒后的目标形态**：`engine/score/` 一个包，三个文件（`scorer.py` / `cross_section.py` / `heat.py`），零 re-export、零转发、零 `sys.path.insert`。`score_stock` 只此一份。

> **红线保护**：推倒的是**结构**，不是**契约**。`score_stock` 的输出字段、评分权重、S3 五档全部原样搬。验收判据 = 同一批股票新旧分数**逐只相等**（允许浮点 1e-9 误差）。

## 10. ★补充发现：红线隐患 —— "数据不出本机"存在一条静默开关

> 本条不在任务清单里，是我在核实 §7 外部数据源时实测挖出来的，**属红线级，优先上报**。

### 事实链（全部实测）

1. `supabase_data.py` 提供 `update_holdings(holdings_list, available_cash)`，内部执行
   `_request("POST", f"{SUPABASE_URL}/rest/v1/holdings", data=...)` —— **把实盘持仓 POST 到远程表**；
   另有 `append_trade_log()` 写远程流水。
2. 调用方**在活跃链路上**：
   - `trade_tracker.py:584`、`trade_tracker.py:622` → `from supabase_data import update_holdings as sb_update`
   - `trade_tracker.py:191`、`trade_tracker.py:209` → `append_trade_log`
   - `portfolio_review.py:21` → `load_holdings`/`is_connected`
   - 而 `trade_tracker` 与 `portfolio_review` 都被 `orchestrator.py`（生产入口）调用。
3. 调用处是**裸 try + 静默吞掉**：
   ```python
   try:
       from supabase_data import update_holdings as sb_update
       sb_update(fresh.get("holdings", []), fresh.get("available_cash", 0))
   except Exception:
       pass          # ← 失败完全无声
   ```
4. **当前未实际外传**：`.env` 只有 `AGNES_API_BASE` / `AGNES_API_KEY`，**没有** `SUPABASE_URL` / `SUPABASE_SECRET_KEY` → `SUPABASE_URL=""` → `is_connected()` 恒 False → 走本地 JSON 降级。

### 判定

- **不是现行违规**（数据当前没出去），但**是"开关式红线隐患"**：只需在 `.env` 补两行，实盘持仓 + 成交流水就会**静默上传远程**，且无任何告警、无任何日志（`except: pass`）。
- 同时它还是**"静默兜底"反面教材**：`except Exception: pass` 让"同步失败"永远不可见。

### 建议处置（需架构师拍板，对应 O-3）

- **删除 supabase 的写路径**（`update_holdings` / `append_trade_log`），`trade_tracker` / `portfolio_review` 改回纯本地 JSON 原子写。
- 读路径一并删除（本地已有权威 `data/holdings.json`，读远程只会引入第二数据源）。
- **把红线做成"能力不存在"，而不是"开关关着"** —— 后者迟早会被某次配置变更打开。
