# pytest 并发风暴根因诊断 · 20261019

> 结论一句话：**不是调度器重试，不是 numba，不是套件慢 —— 是 `scripts/test_git_sync_gate_logic.py`
> 自己调用生产门禁函数，而门禁函数会把「含自己在内」的 18 个测试文件丢给 pytest，形成自递归
> fork 弹（fork bomb）。实测递归深度 34 层、每 3.4 秒 +1 个进程。**

诊断性质：只读诊断，**未修改任何代码，未 kill 任何进程**。

## 一、发起者（文件:行 + 铁证）

全仓 grep（限定 `scripts/`，已避开 `backups/` `node_modules/` `_archive/`）：

| `scripts/git_sync_task.py:74` | `subprocess.run([sys.executable, "-m", "pytest"] + files + ["-q"], ...)` |

### 1.2 递归闭环：测试文件在 pytest 内部再次调用它


`TestGateFunctionDirectly`（`test_git_sync_gate_logic.py:181-203`）的 docstring 写得很直白：
「直接调用生产函数 run_pytest_gate, 不通过 main()」。**这就是弹。**

（00:47 / 01:02 / 01:17 / … / 05:32）。放大器是：

`data/self_heal.log` 实证（每 15 分钟一条）：

## 二、累积机制（实测：线性链、每 3.4 秒 +1、深度 34）

### 2.1 现场抓拍（2026-10-19 05:47:15 那一轮， live）

`Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 顺 ParentProcessId 上溯：

```
TOTAL_PY=49   （其中 48 个是弹链，1 个是 Hermes 自身的 python）

PID=10352 PPID=7760   05:47:15  python.exe "D:\open code\zhuanqian\scripts\git_sync_task.py"   ← QSP_GitSync 根
PID=7896  PPID=10352  05:47:15  python.exe -m pytest <18个文件> -q      ← D0
PID=11076 PPID=7896   05:47:20  python.exe -m pytest <18个文件> -q      ← D1
PID=21904 PPID=11076  05:47:23                                          ← D2
PID=23060 PPID=21904  05:47:27                                          ← D3
...
MAX_DEPTH = 34
D33 PID=6936  PPID=2104  05:49:15
D34 PID=2136  PPID=6936  05:49:19
```

**形态判定**：不是二叉树，是**深度优先的线性链** —— 每层只派生 1 个子进程。
原因：pytest 串行跑用例，`test_run_pytest_gate_returns_enriched_result` 派生后阻塞等待，
子树跑完才轮到下一个用例，于是深度逐层 +1。

**启动时间分布（实测间隔）：**

```
D0 05:47:15 → D34 05:49:19   共 124 秒
每层间隔 3~4 秒（3.4s 均值），稳定、无收敛趋势
```

即：**每 3.4 秒净增 1 个 python.exe，且永不回落**，直到最深层 600s 超时才开始回卷。
这精确解释了「19~48 个」这个观测区间 —— 抓拍时刻不同，深度不同（本次抓到 49/37 两次数值）。

### 2.2 是否挂起？是，且超时后留孤儿

`git_sync.log` 里 **`TimeoutExpired` 出现 20 次**：

```
subprocess.TimeoutExpired: Command '['...python.exe', '-m', 'pytest',
  'D:\open code\zhuanqian\scripts\test_atomcode_bridge.py', ... 共18个 ..., '-q']'
  timed out after 600 seconds
```

挂起位置：`scripts/git_sync_task.py:74` 的 `subprocess.run(..., timeout=PYTEST_TIMEOUT)`，
`PYTEST_TIMEOUT = 600`（`:42`）。链条每层都带着自己那 600s 预算阻塞等待下一层，
**所以整棵树是「全部挂起、互相等待」，不是并发计算**。

**孤儿机制**：Windows 上 `subprocess.run` 超时走 `Popen.kill()` → `TerminateProcess`，
**只杀直接子进程，不杀孙进程**。父层超时被杀后，D1..D34 整条链失去监管继续存活并继续派生。
这就是「明明计划任务是 09:30/15min 一次，却在任意时刻都能看到几十个 python.exe」的原因。

### 2.3 不是并发，是串行自递归（关键区分）

- 不是「十几个调度器同时启动」：全仓只有 1 个 pytest 派生点。
- 不是「18 文件 1:1 映射 18 进程」：是同一条命令被**自己**重复执行。
- 不是 numba/CPU 争用：见第三节，套件本体只要 **8 秒**。

## 三、「查清前全量 pytest 结论不可信」的判据

### 3.1 决定性对照实验（本次实测）

| 组合 | 结果 | 耗时 |
|---|---|---|
| **17 个文件**（`scripts/test_*.py` 剔除 `test_git_sync_gate_logic.py`） | **93 passed, 43 warnings** | **8.03s**（wall 12s） |
| **18 个文件**（门禁实际跑的，含弹文件） | **93 passed / 5 failed, 43 warnings** | **539.32s**（05:17 那轮，`git_sync_state.json` 实锤） |

**passed 数一模一样（93）、warnings 数一模一样（43）。**
唯一变量就是 `test_git_sync_gate_logic.py` 这一个文件：它贡献了 **5 个失败 + 531 秒**。

> 也就是说：所谓「全量 pytest 跑到 63% 后 40+ 分钟不收敛」= 在测一个 fork 弹，
> 不是测代码。套件本体 8 秒跑完、全绿。

### 3.2 那 4 个「并发假象」失败项其实是确定性 stale-API 失败

不是 flaky，单独重跑也**不会**因为「不争用」而变绿 —— 它们是代码与已删除 API 脱节：

| 失败用例 | 真实原因 |
|---|---|
| `TestGateFunctionDirectly::test_run_pytest_gate_returns_enriched_result` | 断言 `note`/`failed_tests`/`pre_existing`/`new_fail` 四个 key（`:191-194`），但 `run_pytest_gate()` 在 files 非空时只返回 `{ok,passed,failed,rc,tail}` → 必然 AssertionError |
| `TestGateFunctionDirectly::test_run_pytest_gate_with_force_reason` | `:200` 传 `force_reason=` 关键字，但 `git_sync_task.py:68` 签名是 `def run_pytest_gate():` → 必然 TypeError |
| `TestPreexistingRedNoBlock` / `TestNewRedBlocksPush` / `TestForceWithReason` | `_copy_prod_to_temp(PROJECT, ...)`（`:40`）拼出 `D:\open code\zhuanqian\git_sync_task.py`，该文件在根目录**不存在**（在 `scripts/` 下）→ `shutil.copy2` 必然 FileNotFoundError |

三个前提叠加 ⇒ 门禁**永远不可能绿** ⇒ 永远不 push ⇒ P-04 永远红 ⇒ 每 15 分钟再弹一次。

### 3.3 判据（重跑全量前的准入检查，不满足则结论作废）

1. `python.exe` 进程数 == 1（只剩 Hermes 自己的那个）：
   `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 计数。
2. `Get-ScheduledTaskInfo -TaskName QSP_GitSync` 的 `LastRunTime` 距现在 **> 15 分钟**，
   且 `QSP_SelfHeal` 未处于「即将 /Run」窗口。
3. 全量命令**必须剔除** `scripts/test_git_sync_gate_logic.py`，或该文件已被修好（见第四节 P0-1）。
4. 若观测到 `python.exe` 计数随时间单调上升（≈3.4s +1），**立即判定结论作废**，且不要 kill 别人的进程。
5. 期间所有「性能/耗时」类用例（如 `tests/test_scan_performance.py`）的结论一律不可信 ——
   CPU 被弹链吃满，超时是环境造成，不是被测代码。

> 补充：`scripts/test_git_sync_gate_logic.py` 目前**未被 git 跟踪**
> （`git ls-files --error-unmatch` 报 `did not match any file(s) known to git`，
> 尽管 `.gitignore:23` 有 `!scripts/test_*.py`）。所以 CI checkout 不会中弹，**弹只在本机出现**；
> 反过来也说明：任何「CI 绿」的结论都不能用来证明本机门禁可绿。

## 四、根治方案（具体到文件和行）

### P0-1 拆掉递归（治本，必做）

**文件：`scripts/test_git_sync_gate_logic.py`**
**改法：删除 `181-203` 行整个 `TestGateFunctionDirectly` 类**（即 `:187` 与 `:200` 两个派生点）。

理由：
- 该文件第 1 行已自称 `DEPRECATED → use scripts/check_all.py backtest-gate`；
- 它测的 `pre_existing`/`new_fail`/`frozen_since`/`force_reason` 在现行 `git_sync_task.py` 里**全都不存在**，
  是纯粹的 stale 测试，删掉不损失任何覆盖；
- 剩下的 3 个类（`:67-178`）因 `:40` 路径 bug 也全红，建议一并删除整个文件。

**预期效果**：门禁从 539s/600s超时 → 回到 **8s**；5 个失败全部消失；弹链归零。

> 若需保留门禁单测，正确姿势是让 `run_pytest_gate` 接受可注入的 `files` 参数，
> 测试传 1 个临时目录里的假测试文件，而**绝不能**让它看到真实的 `scripts/test_*.py`。

### P0-2 门禁自身加递归护栏（防复发，必做）

**文件：`scripts/git_sync_task.py`**
在 `run_pytest_gate()`（`:68`）开头加哨兵，并在 `:78` 的 `env` 里带上哨兵让子进程继承：

```python
# :69 前插入 —— 递归护栏: 门禁子进程内不得再起门禁
if os.environ.get("ZQ_PYTEST_GATE"):
    return {"ok": False, "passed": 0, "failed": 0,
            "note": "拒绝递归调用(已在 pytest 门禁子进程内)"}

# :74 的 env 改为
env={**os.environ, "PYTHONPATH": "", "ZQ_PYTEST_GATE": "1"}
```

**预期效果**：即使将来再有人写出「测试里调生产门禁」的代码，也只会拿到一个
`ok=False` 的假绿拒绝，不会再派生进程。这是**唯一能防住同类复发**的改动。

### P0-3 门禁清单排除自身（顺带）

**文件：`scripts/git_sync_task.py:70`**
`files` 过滤掉 `test_git_sync_gate_logic.py`，或改为显式白名单。
（P0-1 删除文件后本条自动失效，可作为兜底保留。）

### P1-1 掐断 15 分钟放大器

**文件：`scripts/self_heal_check.py:738`**
P-04 目前复用 R-03（`:673`）→ `schtasks /Run QSP_GitSync`，且无任何冷却。
改为：给 P-04 独立 repair，并加 **≥6h 冷却**（同 P-01/P-06 已有的节流写法），
避免「修不动就每 15 分钟再修一次」。

**预期效果**：即使门禁仍红，也不会每 15 分钟拉起一次弹；机器从「持续满载」降到「09:30 一次」。

### P1-2 超时要杀整棵树，别只杀直接子进程

**文件：`scripts/git_sync_task.py:74`**
`subprocess.run(..., timeout=600)` 超时后只 kill 直接子进程，孙进程成孤儿（本次实测孤儿链就是这么来的）。
改为 `try/except subprocess.TimeoutExpired` 后按 PID 杀树：

```python
taskkill /PID <child.pid> /T /F
```

**预期效果**：超时后不再遗留孤儿链，`python.exe` 计数能真正归零。

### P1-3 门禁失败要能区分「真红」与「环境红」

**文件：`scripts/git_sync_task.py:88`**
`ok = (r.returncode == 0) and failed == 0` 目前把「弹链超时」也记成普通红，
而 `emit_alerts` 又把它升成 P0 推送 → 与 self-heal 的 P0 阈值互相放大。
建议对 `TimeoutExpired` 单独出 `note="门禁超时(疑似递归/环境)"` 且不走 P0 推送。
