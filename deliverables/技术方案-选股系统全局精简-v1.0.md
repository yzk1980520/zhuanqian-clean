```
│   ├─ daily.py  weekly.py  health.py  evolve.py  intraday.py  drain.py
├─ engine/                 纯计算层：无 IO、无告警、不读 holdings

│   ├─ score/              scorer / cross_section / heat
│   ├─ strategy.py
│   ├─ risk/               rules.py ★红线唯一权威源★ / stop.py
│   ├─ market.py / filter.py
│   └─ backtest/           rotation → engine → fast_inds ★保留分层，禁止合并★
├─ pipeline/               唯一允许写 data/ 的业务层
│   pick / review / alerts / trades / diagnostics
├─ ops/                    schedule(22任务注册表) / watchdog(三狗合一) / notifier / gate / audit
├─ shared/                 atomic_io / config / calendar / lock / log
```

### 2.2 依赖方向规则（**禁止反向**，违反即 CI 红）

```
app  →  pipeline  →  engine  →  shared
ops  →  shared  （ops 只读 data/，不得写业务数据）
research  →  engine/shared ，且 生产层 ──X──> research（禁止）

单向公约：
  shared   不得 import 任何上层
  engine   不得 import pipeline / app / ops，不得读写 data/
  pipeline 是唯一写 data/ 的层（holdings/trade_log 仍受"总管独占写"约束）
  ops      不得 import pipeline（避免监控被监控对象拖垮 —— B-3 教训）
```

### 2.3 破除循环依赖环（**本方案骨架问题**）

**现有环 [实测]**：
```
tdx_core → tdx_score → tdx_score_original → tdx_indicators → pattern_recognition → tdx_core
tdx_core → integrated_picker.helpers → tdx_core
risk_rules → risk_rules_engine / _adapter / _config
```
根因：**数据获取层反向 import 了评分层/选股层**。

**破环方案一句话**：
> 把"被下层反向引用的能力"下沉到 `shared/` 或 `engine/data/`，上层改为从下沉模块 import；
> `tdx_core` 拆为 `engine/data/source.py`（纯读取）+ `shared/indicators.py`，
> `tdx_score_original` 与 `tdx_score/*` 收敛为 `engine/score/` 单一包后，环自然消失。

**分步（每步独立可回滚）**：
1. 建 `shared/` 空包，把 `atomic_json`（→`shared/atomic_io.py`）、`config_loader`、交易日历下沉
2. `tdx_indicators` / `pattern_recognition` 下沉到 `engine/data/`，切断它们对 `tdx_core` 的反向引用
3. `tdx_score` 整族重写为 `engine/score/`（见 §2.4），`tdx_core` 退化为薄 re-export 或直接删除
4. `risk_rules` 三件套（`_engine`/`_adapter`/`_config`）并入 `engine/risk/rules.py` 单文件

### 2.4 `tdx_score` 整族推倒重来（**本方案唯一批准的"重建"**）

采纳信息架构建议。现为四层洋葱：
`tdx_core` → 包 → （一半自己实现 / 一半转发 `tdx_score_original`）→ `tdx_score.py` re-export → `_score_engine` 再转发。
**干活的是最底层，每层都是"为了不动调用方"加的**，是"改了没生效"的温床。
同一作者、同一时间点（2026-09-23 Phase C-2）、同一手法已在 `integrated_picker` 上爆过一次
（`import integrated_picker` 解析到**包**的 11 元组简化版，而非根目录 `.py` 的 20 元组完整版；
`orchestrator.py:206-213` 被迫用 `spec_from_file_location` 手工硬加载绕过）。

**推倒的是结构，不是契约**：`score_stock` 输出字段/权重/S3 五档原样搬。
**验收判据**：同批股票新旧分数**逐只相等**（1e-9 容差）。

## §4 接口契约（冻结 · 失败必须 loud）

**总原则：禁止静默兜底。** 本项目已因此多次"系统说谎"
（`[实测]` 三例：supabase 外传裸 `except: pass`；止损 `contract.get(..., 0.08)` 静默回退旧口径；
时间止损日期解析失败 `return False` 谎报"未触发"）。

### 4.1 硬规则

1. 禁止 `except Exception: pass` / `except: pass`
2. 禁止 `return False/None/0` 表示"算不出来" —— 必须 `raise`
3. 禁止 `dict.get(key, <业务默认值>)` 用于**契约数值**（止损/止盈/阈值）；
   允许用于纯展示默认值，但缺失时必须打 warning
4. `Optional` 返回必须文档化"None 表示什么"

### 4.2 关键接口签名（冻结）


### 4.3 单位规范（**本项目特有陷阱，必须写进注释**）

止损在不同模块有**两套单位**：
- `risk_rules` / `holdings.json`：**小数**（0.10）
- `_get_stop_loss_pct()` / 展示层：**百分数**（10.0）

**契约**：函数名带 `pct` 且无前缀的返回小数；`_get_stop_loss_pct` 因历史原因返回百分数，
**必须在 docstring 标注**。跨单位传递处必须显式 ×100 或 ÷100。

## §6 收编技术方案（外部 `.quant-stock-picker`）

### 6.1 范围与排除

- **收**：外部 `src/` 39 个模块中，与仓库无同名且确有活跃价值的（需求说明书 §4.3.C 分类表）
- **不收（直接废）**：外部自带的 **4 个 adapter 冗余 + 5 个过度设计层**
  （`di_container` / `protocols` / `nlp_intent` / `param_guard` / `gate_mode`）
  依据：老大"不留兼容层、不留 alias、不留适配层"授权 + 铁律 1 简洁为荣
- **排除**：`holdings` / `trade_log` 副本 —— **只比对不覆盖**（红线 G4）
  `[实测]` 已分叉：主仓 10-15 仍持仓 sh603727(300股)，外部 10-07 空仓

### 6.2 `atomic_json` 合并 —— **第一风险，禁止覆盖**

| API | 仓库版（184行） | 外部版（110行） |
|---|---|---|
| `atomic_dump` | ✅ | ✅ |
| `atomic_load` | ✅ | ✅ |
| `atomic_load_raise` | ❌ | ✅ |
| `update_json` | ✅（`orchestrator.py:313` 活跃生产入口在用） | ❌ |
| `FileLock` 类 | ✅ | ❌ |
| 锁实现 | `FileLock` 类 + 线程锁 | **fd 文件锁** |

**约束 C9：禁止任何形式的覆盖合并。**
- 谁覆盖谁都破：外部版盖仓库版 → `orchestrator.py:313` ImportError 主链路当场断；反之 → 外部 8 个任务崩
- **破坏是静默的**：import 名不变，grep / 路径映射 / 行数指标全抓不到
- **最坏后果是数据损坏**：两版锁协议不同（fd 锁 vs FileLock），并发写同一文件时锁互不识别
  → **实盘持仓静默写坏，不报错**

**合并方案**：
1. 结果必须是 **API 并集**：`atomic_dump` / `atomic_load` / `atomic_load_raise` / `update_json` / `FileLock` 五个符号全在
2. **锁协议统一到 `FileLock`**（仓库版），外部 fd 锁实现删除
3. 收编前静态扫全部 `from atomic_json import X`，X 必须在合并版存在
4. 过断言 **B9** 才允许继续：
   ```bash
   python -c "import atomic_json as a; assert all(hasattr(a,n) for n in ['atomic_dump','atomic_load','atomic_load_raise','update_json','FileLock'])"
   ```

## §7 告警链路重建（F-018）+ 调度统一（F-019）

### 7.1 为什么是告警链路重建（判据）

> **组件内嵌领域价值越低（越接近纯管道）越适合推翻重建；内嵌策略语义越重越应改造。**

按此主动排除：`integrated_picker`（2557 行嵌选股语义）→ 改造；
回测 5 件套（嵌 132 日判据）→ 改造。**告警链路是纯管道、零契约数值 → 重建。**

### 7.2 重建设计

```
现状：30 个文件各自写队列 + 4 套写口 + 1 消费口
目标：1 写口(pipeline/alerts.add_alert) + 1 消费口(ops/notifier.drain_queue)
```

**执行顺序硬约束**：
- **禁止先拆后建**：旧链继续跑，新链并行验证，切换时原子切
- **F-018 与 F-019 必须绑定**：停摆根因是调度（B-3），不是链路本身。
